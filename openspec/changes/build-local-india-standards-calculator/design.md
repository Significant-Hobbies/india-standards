## Context

This is a greenfield standalone local experiment. The product requires highly
interactive filters, server-side analytics, and a local database, so the
requested Next.js App Router stack is appropriate. Official PLFS files require
login and NFHS microdata has separate access controls; neither will be
committed.

## Goals / Non-Goals

**Goals**

- Exercise the full calculator interaction against a real DuckDB query.
- Preserve a strict distinction between joined demographic filters and modelled
  height.
- Implement best-effort sparse-cell ranges and a numeric range-precision score, not
  just a happy path.
- Make result URLs shareable without storing personal input.
- Define a narrow normalized import contract for official data later.

**Non-Goals**

- Produce an official population estimate from generated demo data.
- Add MotherDuck, authentication, telemetry, deployment, or a data-download UI.
- Add excluded dating, health, community, or city-level dimensions.

## Decisions

### Next.js route handler as the local backend

Use an App Router POST route with the Node runtime. It keeps DuckDB server-only
and lets the interactive client share types with validation and result
formatting code. A separate Python web service would add a second process
without improving this local experiment.

### DuckDB Node Neo

Use `@duckdb/node-api`, DuckDB's current promise-based primary Node client. A
single cached instance points at a generated local file. Queries use bound
parameters. The database is generated by an explicit seed command rather than
being created during a web request.

### Aggregate demo cube plus conditional height table

The generated demographic cube stores joint cells across the supported exact
dimensions, income bands, weighted estimates, unweighted observations, and
deterministic uncertainty factors. A separate height table stores conditional
normal-model parameters by gender, age band, State/UT, and area. The server
sums matching demographic cells and applies the height interval probability.

This matches the intended production boundary while avoiding synthetic
person-level records. Accuracy and coverage take priority over storage size:
joint cells remain intact because multiplying independent marginals would erase
correlations. Storage optimization is allowed only when output-equivalence is
validated against the full cube.

### Range construction

The demo cube carries deterministic lower/upper replicate-style weights and the
height model carries lower/upper probability bounds. The API combines the
appropriate corners into a conservative interval, widens high-income results,
widens sparse cells, and rounds to no more than three significant digits. A
0–100 range-precision score is derived from the final interval's relative
half-width; it is explicitly not a probability that the estimate is correct.
These demonstrate the bootstrap contract but are not labelled as survey
confidence intervals.

### Workbench interaction

Use the owner-delegated Direction C. Desktop puts compact filters above a single
result canvas; mobile shows the result first and composes controls underneath.
Borrow Direction A's explicit filter controls. Do not literalize generated mock
icons, fake numbers, heart symbols, or any claim that generated values are PLFS
observations.

## Risks / Trade-offs

- Demo estimates can look plausible despite being synthetic. Persistent data
  mode labels, methodology copy, and a first-run notice mitigate this.
- Income bands make minimum thresholds discrete. The UI uses the same supported
  breakpoints and does not imply rupee-level resolution.
- A native DuckDB dependency limits browser-only/static hosting. That is
  intentional for the local experiment and can later map to MotherDuck or a
  hosted aggregate API without changing the calculation contract.
- Normal-distribution height probabilities are a simplified demo of the future
  NFHS conditional model.

## Migration Plan

1. Seed the generated local database.
2. Run representative estimation tests and the Next.js build.
3. Later, add explicit PLFS/NFHS import scripts behind the same normalized
   tables and validation manifest.
4. Switch UI data mode to `official` only after sample/weight totals and source
   mappings pass documented checks.

No production migration or rollback is needed for this local-only app.
